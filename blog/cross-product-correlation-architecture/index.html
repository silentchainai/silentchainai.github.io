Cross-Product Correlation Architecture: Enterprise + SOURCE + Sn1per → RAG → Escalation Rules

Three scanners. Three surfaces. One RAG engine. Ten escalation rules. A product-wiring walkthrough of how SILENTCHAIN Enterprise, SILENTCHAIN SOURCE, and Sn1per each feed the correlation engine - and how a quiet Medium in one tool becomes a corroborated Critical once the others check in.

Why Single-Surface Scanners Miss the Chain

A reflected url parameter is a Medium SSRF when a DAST scanner sees it in isolation. The same parameter, when a SAST scanner confirms it reaches requests.get in proxy.py with no sanitization, is a High. The same parameter again, when a network scanner confirms the target can reach 169.254.169.254 on an AWS EC2 instance, is a Critical with a cloud-metadata exfil path two HTTP requests away from a shell.

Three findings, three tools, three severities. One exploit. Every AI security scanner on the market today stops at step one - because each scanner only sees its own surface. SILENTCHAIN's correlation architecture exists to stitch the surfaces together at ingest time, not at triage time. The rest of this post walks through how each product in the stack wires into the RAG engine, what data travels across the boundary, and how the escalation rules turn corroborated evidence into an actionable severity bump.

Note: this is the product-wiring view. For the correlation algorithm, context store internals, and PoC generation, see our earlier engineering deep-dive. This post focuses on how each product calls in, what the payloads look like, and what the customer sees at the end.

The RAG engine exposes two endpoints that matter for correlation: POST /ingest/context accepts typed context payloads keyed on the normalized target, and POST /correlate evaluates a finding against all known context for that target. Each product handles its own auto-wiring - the correlation is not a separate tool the user has to bolt on. It runs inline with every scan.

The shared piece of infrastructure is a small client library, silentchain-ai-core, which every product imports. The client exposes three methods - ingest_context(), ingest_context_bulk(), and correlate() - so each product talks to the RAG engine through a single, versioned contract. When the contract changes, every scanner upgrades together.

SILENTCHAIN Enterprise → Surface & Traffic Context

Enterprise is the DAST edition. It crawls web applications, identifies parameters, detects WAF fingerprints, and captures live HTTP traffic. Inside the scan engine, two auto-wired hooks fire against the RAG engine: one during reconnaissance (surface context), one during authenticated request capture (traffic context). 

# enterprise/scanning/context_ingest.py
await rag_client.ingest_context(
    target="https://app.example.com",
    context_type="surface",
    evidence_type="waf_fingerprint",
    data={
        "urls":        ["/api/proxy", "/admin/config", "/api/users"],
        "parameters":  ["url", "callback", "redirect", "id"],
        "waf":         "none",
        "frameworks":  ["express", "node"],
    },
    source="silentchain-enterprise",
)

The surface context captures every URL discovered by the crawler, every parameter name seen in any request, and the WAF fingerprint (or its absence). waf: "none" is a specifically-escalation-relevant string - the RCE + No WAF rule keys off this exact pattern.

At finding creation time, Enterprise calls correlate() with the finding payload and uses the returned escalation decision to update the finding record before it reaches the triage UI: 

response = await rag_client.correlate(finding)
finding.original_severity = finding.severity
finding.severity          = response.escalated_severity
finding.escalation_rules  = response.rules_fired
finding.correlation_data  = response.evidence
db.save(finding)
event_bus.emit("EVENT_FINDING_CREATED", finding)

Three new fields land on the Finding model - original_severity, escalation_rules, and correlation_data - and flow straight through the REST API to the web UI. The triage panel renders an escalation badge, a list of rules that fired, and a "corroborating evidence" expander so an analyst can audit the promotion before acting on it.

SILENTCHAIN SOURCE → Code Context

SOURCE is the SAST edition. Its discovery phase walks the codebase, identifies dangerous sinks, and builds taint flows. The code context payload looks materially different from Enterprise's, because the evidence types differ: 

# source/scanning/context_ingest.py
await rag_client.ingest_context(
    target="https://app.example.com",
    context_type="code",
    evidence_type="vulnerable_sink",
    data={
        "file":        "proxy.py",
        "line":        42,
        "sink":        "requests.get",
        "taint_flow":  ["request.args['url']", "url", "requests.get(url)"],
        "sanitizers":  [],
    },
    source="silentchain-source",
)

The sink field is the high-signal one: the code extractor in the correlation engine looks for an exact list of dangerous identifiers (exec, eval, system, subprocess, requests.get, urllib, os.popen, cursor.execute). When a SOURCE sink matches a DAST vulnerability class, the rule engine has everything it needs to fire the File Upload + Server-Side Execution or SQLi + DB Credentials escalations.

SOURCE also binds a target identifier at scan time - typically the repository's deployed URL when known, or the Git remote URL when not. Matching this to the DAST target identifier is the linchpin of cross-product correlation. If a repo has no known deployment URL, correlation still works through the multi-product corroboration rule, which counts distinct source labels instead of surface joins.

Sn1per → Network Context

Sn1per is the network reconnaissance edition. Its ingestion path is the oldest of the three - it existed before the correlation engine shipped - so the auto-wiring lives in a shell wrapper in modes/functions.sh: 

# sn1per/modes/functions.sh (auto-wired)
rag_ingest_network_context() {
    TARGET=$1
    PORTS=$(grep ^Port "$LOOTDIR/nmap.txt" | awk '{print $2}' | paste -sd ',')
    SERVICES=$(awk '/open/ {print $3}' "$LOOTDIR/nmap.txt" | sort -u | paste -sd ',')
    TECHS=$(grep -oP 'Server: \S+' "$LOOTDIR/http.txt" | sort -u | paste -sd ',')

    curl -sX POST "$RAG_URL/ingest/context" -H 'Content-Type: application/json' -d "$(cat <<EOF
{
  "target":        "$TARGET",
  "context_type":  "network",
  "evidence_type": "nmap_scan",
  "data": {
    "ports":        "$PORTS",
    "services":     "$SERVICES",
    "technologies": "$TECHS"
  },
  "source": "sn1per"
}
EOF
)"
}

The network extractor in the correlation engine is the one that finds 169.254.169.254, RFC 1918 internal IPs, and service names like Redis, Elasticsearch, and memcached in the ingested text. Those are the strings that the SSRF + Internal Services and SSRF/RCE + Cloud Metadata escalations trigger on.

Sn1per's findings also flow through /correlate. A port scan confirming Redis on 10.0.0.5:6379 is, by itself, a low-severity information disclosure. When an SSRF finding lands from Enterprise for the same target, both findings get re-correlated - the SSRF's severity jumps to Critical, and Sn1per's Redis finding gets a +0.20 confidence boost from the multi-product corroboration rule.

Target Normalization: The Unsung Load-Bearing Detail

Three products, three target formats. Enterprise sees https://app.example.com:443/. SOURCE sees app.example.com from the repo config. Sn1per sees 192.168.1.50 after resolving. If any of these fail to converge, the correlation engine silently misses the join and the escalation never fires.

Every ingest and every correlate call passes through normalize_target(), which lowercases, strips scheme and default ports, collapses trailing slashes, and preserves non-default ports. http://10.0.0.5:8080/ and 10.0.0.5:8080 land on the same target_id. https://app.example.com and http://app.example.com:443 also land on the same ID. If a real deployment runs on a non-default port, we keep the port - we do not silently collapse :8080 to nothing.

This single function is the reason correlation works at all. We have a longer discussion of target normalization, idempotent ingestion, and the metadata-filter-vs-vector-search decision in the earlier engineering deep-dive. For this post it is enough to know: it is the load-bearing plumbing.

The Ten Escalation Rules (What the Engine Looks For)

When a finding is correlated, the engine walks ten rules. Each rule is a triple of (vuln-type trigger, required context types, regex evidence patterns). A rule fires only when all three conditions hold. Severity escalation is monotonic - once a finding is promoted to Critical, no later rule can downgrade it.

Rule Trigger Evidence Sourced From Escalation
SSRF + Internal Services SSRF, CWE-918 Sn1per (internal IPs, Redis/memcache/elasticsearch) Critical
SSRF/RCE + Cloud Metadata SSRF, RCE, CWE-918, CWE-78 Sn1per (169.254.169.254, metadata.google) Critical
SQLi + Captured Traffic SQLi, CWE-89 Enterprise (captured parameter in live traffic) High
SQLi + DB Credentials in Code SQLi, CWE-89 SOURCE (password, db_pass, connection strings) Critical
RCE + No WAF RCE, command/code injection Enterprise (WAF fingerprint: none) Critical
Auth Bypass + Admin Panels Auth bypass, IDOR, CWE-287, CWE-306 Enterprise (/admin, /dashboard, /console) Critical
XSS + Session Theft XSS, CWE-79 Enterprise (Set-Cookie without HttpOnly) High
File Upload + Server-Side Execution File upload, CWE-434 SOURCE (exec/eval/include sinks, .php/.jsp paths) Critical
LFI + Sensitive Files LFI, path traversal, CWE-22 Sn1per (/etc/passwd, .env, wp-config) Critical
Multi-Product Corroboration (any vulnerability type) Any 2+ distinct source labels +0.20 confidence boost

Every escalation emits a CorrelationEvidence payload - the rule name, the contributing findings, and the raw context documents that matched the evidence regex. Nothing is ever silently upgraded. A security analyst can always answer the question "why is this Critical?" by expanding one row in the triage panel.

What the Customer Sees

Everything above is plumbing. Here is what lands in front of a user:

  1. Enterprise triage panel renders an escalation badge with original_severity → escalated_severity, a row of rule pills showing which rules fired, and an "evidence" section listing the corroborating findings from other products.
  2. Unified Findings Dashboard (at /dashboard on the RAG engine) aggregates findings from Enterprise, SOURCE, Sn1per Pro, and Sn1per Enterprise into one view. Filter by severity, source, target, or triggered rule.
  3. Attack chain narratives in PoC reports attribute every stage of the exploit to the tool that contributed the evidence - "Sn1per confirmed Redis on 10.0.0.5:6379," "SOURCE confirmed requests.get(url) in proxy.py:42," "Enterprise confirmed no WAF on /api/proxy."

Three dashboards collapse into one. Three triage queues collapse into one. And the twelve findings in a 200-finding backlog that actually matter surface at the top, automatically, on every scan.

Why This Is the Moat

Every AI security vendor in 2026 is running the same playbook: LLM-assisted classification on a single surface. DAST vendors add LLM to DAST. SAST vendors add LLM to SAST. Network vendors add LLM to nmap. The race is to the best prompt on the same input.

SILENTCHAIN's bet is different. The LLM is not where the leverage is - the cross-product context is. A Medium SSRF in DAST is correctly a Medium. A Medium SSRF that SOURCE confirms hits requests.get and Sn1per confirms can reach cloud metadata is correctly a Critical. No single-surface LLM can make that call, because no single-surface LLM has the evidence. Correlation is the moat.

Ten rules today. The architecture is additive - new rules plug into the same engine, the same context store, the same ingestion contract. The product-wiring described above does not change when a rule is added. It changes when a new surface joins the stack, which is a larger piece of work, and one that we are already roadmapping.
